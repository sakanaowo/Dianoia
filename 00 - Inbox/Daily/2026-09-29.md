# 1. Foundations: Observability & 3 pillars 

**Observability** là khả năng hiểu _trạng thái nội bộ_ và _lý do_ agent ra quyết định, chỉ từ dữ liệu nó phát ra (traces, logs, metrics, evals). Nó trả lời được cả những câu hỏi bạn chưa lường trước, chẳng hạn "Vì sao agent gọi tool này 7 lần rồi vẫn trả lời sai?"

**Monitoring** là theo dõi các chỉ số _đã định nghĩa trước_ và cảnh báo khi vượt ngưỡng. Nó trả lời "hệ thống có ổn không?".

| Tiêu chí    | Monitoring                                      | Observability                                                                   |
| ----------- | ----------------------------------------------- | ------------------------------------------------------------------------------- |
| Câu hỏi     | _Cái gì_ hỏng?                                  | _Tại sao_ hỏng?                                                                 |
| Loại vấn đề | Known-unknowns                                  | Unknown-unknowns                                                                |
| Dữ liệu     | Metrics tổng hợp (latency, error rate, token/s) | Trace đầy đủ từng bước, prompt/response, tool I/O                               |
| Cách dùng   | Dashboard, alert theo ngưỡng                    | Truy vấn ad-hoc, drill-down, replay                                             |
| Với agent   | "Error rate = 3%"                               | "Ở step 4 retriever trả về doc sai → LLM hallucinate → tool bị gọi sai tham số" |

### ![[Pasted image 20260929102850.png]]3 Pillars + Profiles

|Signal|Là gì|Trả lời câu hỏi|Ví dụ với agent|
|---|---|---|---|
|**Logs**|Sự kiện rời rạc, có timestamp|_Chuyện gì đã xảy ra?_|Prompt, completion, tool args, guardrail hit|
|**Metrics**|Số liệu tổng hợp theo thời gian|_Hệ thống đang thế nào?_|Latency p95, token/run, cost, tool success rate|
|**Traces**|Cây span của một request end-to-end|_Đi qua đâu, mất bao lâu?_|`agent.run` → `step` → `llm.call` / `tool.call`|
**Cardinality** là **số lượng giá trị khác nhau (unique)** của một tập dữ liệu. Trong observability, nó là số **time series duy nhất** được tạo ra từ một metric.

Một metric = tên + tổ hợp các label. Mỗi tổ hợp label khác nhau là một time series riêng.

```
llm_requests_total{model="gpt-4", status="200"}   → series 1
llm_requests_total{model="gpt-4", status="500"}   → series 2
llm_requests_total{model="claude", status="200"}  → series 3
```

**Cardinality của metric = tích số giá trị của từng label**:

```
model (5) × status (4) × tool (20) = 400 series   ← OK
```

### Low vs High cardinality

|            | Low cardinality                       | High cardinality                                            |
| ---------- | ------------------------------------- | ----------------------------------------------------------- |
| Số giá trị | Ít, hữu hạn, biết trước               | Nhiều, tăng không giới hạn                                  |
| Ví dụ      | `model`, `status`, `tool_name`, `env` | `user_id`, `session_id`, `trace_id`, `prompt`, `request_id` |
| Hợp với    | **Metrics**                           | **Traces / Logs**                                           |

### Vấn đề: cardinality explosion

Mỗi series tốn RAM, storage, CPU khi query. Nhét label high-cardinality vào metrics sẽ làm:

- Chi phí storage tăng vọt (SaaS như Datadog tính tiền theo số series)
- Prometheus OOM, query chậm
- Dashboard timeout
